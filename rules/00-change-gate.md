# 变更门控（最高优先级硬约束）

**优先级最高，不可被任何 Skill / 子流程 / 后续指令降级或绕过。**

## 一、模糊性门控（Uncertainty Gate）

任何动作之前（不限于文件变更）：若需求、范围或方案存在歧义，立即停止并提一个聚焦问题。
严禁猜测、假设或以"尽力而为"的方式继续。

---

## 二、文件变更前置确认

任何 `Write` / `Edit` / `MultiEdit` 之前，**必须** 通过 `AskUserQuestion` tool 上下键选择获得显式确认。

### 确认流程

| 变更类型 | 流程 |
|---|---|
| 多文件 / 复杂变更 | 编号计划 → AskUserQuestion 确认 → 完整 diff → AskUserQuestion 确认 → 执行 |
| 单文件 / 简单变更 | 完整 diff → AskUserQuestion 确认 → 执行 |

### 唯一允许的确认形式

`AskUserQuestion` 单选，至少包含两个选项（"确认修改" / "取消"），并附变更摘要或 diff 描述。

### 绝对禁止

- ❌ 纯文本 "回复 Y 执行" / "确认后执行" / "OK 吗？" / "好的"
- ❌ 从沉默或上下文推断同意
- ❌ 先执行再补确认

### 违规处理

发现违规 → 已执行的变更视为未授权，立即报告用户并等待指示。

---

## 三、变更后强制 Code Review

每次代码变更落地后，**必须**通过 `Agent` tool 启动独立 sub-agent 对**本次改动的增量 diff**进行审查。
**主 agent 自检 ≠ CR，视为流程违规。**

> **审查范围强制约束（防止重复扫描）：** sub-agent 审查范围仅限**本次落地的增量变更**，**禁止**依赖
> `/code-review-single` 无参数时的"源分支全量"回退（`git diff "$O_BR" HEAD`）——该模式会 diff 当前
> 分支相对源分支的全部累积改动，导致会话内每多一次 Edit，下一次 CR 就要重新审查前面所有已审查过的
> 内容，耗时随改动次数呈平方级增长。
>
> 正确做法：主 agent 自行构造本次改动的 diff（`git diff -- <本次改动文件>`，或直接使用刚
> Write/Edit 前后的内容），连同内联的
> [review-rules.md](../skills/code-review-single/references/review-rules.md) 六维扫描规则与
> [report-template.md](../skills/code-review-single/references/report-template.md) 输出模板一起
> 传入 sub-agent prompt（或写入临时文件供 Read），由 sub-agent 仅基于该增量 diff 审查，不触发
> `/code-review-single` 的 Step1 分支级提取脚本。

> **上下文补充许可：** sub-agent 判断增量 diff 中的问题时，若需要跨函数/跨调用点的一致性上下文，
> 可自行 Read 本次改动文件的完整当前内容（file 级别，非全量分支 diff），不得 Read 改动文件之外的
> 其他文件，不得执行 `git diff`/`git log` 等命令。**`SHARDS > 1` 时，"改动文件"特指该 sub-agent
> 自己分片内的文件，不包含分配给其他分片的文件。**

> **分片与 agentType 分级约束：** 按本次增量 diff 行数（Step 1 净改动行数）与改动文件数决定 `SHARDS`：
> - `diff行数 ≤ 300` 或 涉及文件数 `≤ 1` → `SHARDS = 1`，`agentType: code-reviewer`，单个 sub-agent
>   审查全量增量 diff（保留跨文件一致性视野）
> - `diff行数 > 300` 且 涉及文件数 `> 1`：
>   - `≤ 600 行` → `SHARDS = 2`
>   - `≤ 1000 行` → `SHARDS = 3`
>   - `> 1000 行` → `SHARDS = 4`
>
> `SHARDS > 1` 时，**主 agent 自己完成分片，不再委派 general-purpose 自行拆分**：
> 1. 按文件分组做贪心装箱（改动行数从大到小排序，依次放入当前累计行数最小的分片），保证各分片行数尽量均衡
> 2. 将每个分片写入临时文件（如 `/tmp/cr_shard_<ts>_<n>.txt`，`<ts>` 取当前时间戳，避免多会话/多轮
>    并发触发时的同名覆盖冲突）
> 3. **单条消息**内并行启动 `SHARDS` 个 `agentType: code-reviewer` sub-agent，每个 prompt 只传自己分片的
>    临时文件路径 + 内联 [review-rules.md](../skills/code-review-single/references/review-rules.md)
>    六维扫描规则，并显式禁止其读取分片文件之外的任何文件、禁止执行 `git diff`/`git log`/`git status`
> 4. 收到全部分片结果后，主 agent 自己合并：按 (文件名字母序, 起始行号升序) 排序、重新编号；文件路径+行号
>    完全一致或问题描述高度相似的条目视为重复，合并为一条并标注涉及的分片来源
>
> 此约束仅限本节门控自动触发场景，不影响手动/临时唤起 code-reviewer 做审查的场景，也不再涉及
> general-purpose 或 `code-review-single` 的分片脚本。

> **本门控场景的输出约束（避免报告文件噪音）：** 启动 sub-agent 时，Prompt 中必须显式追加：
> "本次为强制门控自动触发的 CR，仅审查下方给出的增量 diff，跳过写入本地报告文件的步骤（不生成
> `<组件>-code-review.md` / `*_code_review.md`），将完整审查报告内容作为你的最终文本直接返回，
> 供主 agent 在对话中展示。"
> 该约束仅适用于本节的门控自动触发场景；用户主动输入 `/code-review-single` 或 `/code-review-multi`
> 显式调用时，仍按 skill 原生行为写入本地报告文件，不受此约束影响。主 agent 收到全文报告后，
> 按 🚫严重→Critical、⚠️改进→High/Medium（视问题描述严重度自行细分）、💡重构→Low 的对应关系，
> 归纳出 Step 3/5 所需的四级摘要表。

> **已知问题持久化：** Step 3/5 中用户未勾选修复的 Critical/High 条目，主 agent 必须追加写入
> `~/.claude/cr-known-issues/<repo-basename>-<repo-root-sha256-12>.md`（`<repo-basename>` 为
> `git rev-parse --show-toplevel` 返回路径的最后一段，仅用于可读性；`<repo-root-sha256-12>` 为该
> 完整路径 SHA-256 哈希的前 12 位十六进制，用于唯一区分同名不同路径的仓库；目录不存在时执行
> `mkdir -p ~/.claude/cr-known-issues/`；跨会话保留，直到被标记修复或用户显式清除；若文件在读取
> 后被并发修改，以「文件路径:行号」为去重键做追加合并写回，不整体覆盖，同一键的问题摘要以最新
> 一次为准）。每次新一轮 CR 启动前，主 agent 先 Read 该文件，将其中条目原文附加进本轮 sub-agent
> 的 prompt 末尾（标注"历史未修复问题，请结合本轮 diff 一并复核，若已被本轮改动修复请在返回中
> 注明"；`SHARDS > 1` 时按文件路径匹配到对应分片，附加进该分片 sub-agent 的 prompt 末尾；若该条目
> 文件未出现在本轮任何分片中，本轮不参与复核，原样保留在持久化文件中，不视为已处理），
> 不计入 Step 1 的行数统计与规模分级。CR 完成后：sub-agent 判断为已修复的条目从文件中
> 移除；仍未修复的保留；本轮新增未勾选的 Critical/High 追加进去（按去重键跳过重复）。展示摘要
> 表格时，历史条目标注来源为「历史未修复」。

### 默认触发原则（黑名单豁免，非白名单触发）

> **任何 `Write` / `Edit` / `MultiEdit` 操作默认触发 CR。**
> 唯一的例外是同时满足下列「文件类型」AND「操作类型」两个机器可验证条件的情况。
> **条件有任何一个不满足，则必须触发 CR，不得自行定性为豁免。**
>
> **执行顺序：** 本段“默认触发”仅在完成 Step 1 规模判定与 Step 2 极小变更分流后生效。
> 已判定为 `< 20 行` 的极小变更时，必须先执行 Step 2 的专属询问，禁止据此直接启动 CR。

#### 豁免黑名单（两个条件必须同时满足）

**条件 A — 文件类型**（以下任一）：
- 纯文档文件：`.md` / `.txt` / `.rst`
- 静态资源：图片（`.png` / `.jpg` / `.svg` / `.gif` / `.ico`）、字体、音视频
- 项目初始化脚本（`setup.sh` / `bootstrap.sh` 等，仅首次运行类脚本）

**条件 B — 操作类型**（以下任一）：
- 仅修改 `pubspec.yaml` 中的 `version:` 字段（无其他行变动）
- 仅添加 / 删除 注释行（`//`、`#`、`/*...*/`、`<!-- -->`），且不含任何可执行代码的新增或改动
- 用户通过 AskUserQuestion 明确选择「跳过 CR」或「不用 review」

#### 禁止自免（CRITICAL）

- 模型**不得自行宣告**某次变更满足豁免条件，必须在对话中展示判断过程：
  ```
  豁免检查：
    条件 A（文件类型）: [具体文件] → ✅/❌
    条件 B（操作类型）: [具体操作] → ✅/❌
    结论: A AND B = true → 豁免 | false → 触发 CR
  ```
- 若条件判断存在任何模糊性 → **默认触发 CR**，不得以"可能符合"为由豁免。

### 会话累积内标（强制兜底）

维护一个会话级计数器，初始值为 **0**：

- 每次 Write/Edit/MultiEdit **触发 CR** → 重置为 **0**
- 每次 Write/Edit/MultiEdit **被豁免** → 计数 **+1**
- **计数 ≥ 3 时**：无论下一次变更是否满足豁免条件，执行前必须先强制触发一次 CR，完成后重置为 0

> 目的：防止连续小改动通过累积豁免绕过所有 CR。

> 极小变更分支（见 Step 2）中用户主动选择的「跳过 CR」不计入本计数器 — 该分支是显式询问后的用户决策，与"自动豁免"是两套独立机制，但受 Step 2 下方「极小变更专属计数器」单独兜底，防止无限绕过。

### 执行流程（按变更规模与严重度分层，最多 2 轮硬上限）

#### Step 1：评估本次变更规模

按本次落地的 net 新增/修改行数（不计纯文档/测试）：

| 规模 | 标识 |
|---|---|
| 极小变更 | < 20 行 |
| 小变更 | 20 – 100 行 |
| 中变更 | 100 – 500 行 |
| 大变更 / 安全敏感 | > 500 行；或命中敏感关键字（auth、crypto、SQL、密钥、token、permission） |

#### Step 2：极小变更分支（< 20 行）— 主动询问是否 CR

变更规模为「极小变更」时，跳过 Step 3 的自动强制 CR，改为使用 `AskUserQuestion` 主动询问用户：

- 展示：改动文件、净增/改行数、一句话摘要
- 选项：`跳过 CR`（推荐，改动量小）/ `仍然执行 CR`

**专属确认不可替代（硬约束）：**
- 必须单独调用一次 `AskUserQuestion`，并使用上述两个 CR 专属选项；禁止复用其他确认结果。
- “确认计划”“确认修改”“开始实施”“提交并推送”等普通授权，即使计划文本提到将执行 CR，也**不等于**用户选择了「仍然执行 CR」。
- 用户作出 CR 专属选择前，禁止调用任何 Code Review Agent。
- 唯一可跳过本次询问的情况是下方极小变更专属计数器已触发强制兜底，或 Step 1 已将变更归类为安全敏感。

处理结果：
- 选择 `跳过 CR` → 直接完成，**不进入 Step 3**，且**不计入**「会话累积内标」计数器；但计入下方「极小变更专属计数器」
- 选择 `仍然执行 CR` → 进入 Step 3，按小变更流程走完整 CR

> 其余规模（小 / 中 / 大变更）不经过本分支，直接进入 Step 3。

**极小变更专属计数器（防止化整为零绕过 CR）**：

维护独立于「会话累积内标」的计数器，初始值为 **0**：
- 每次在本分支选择 `跳过 CR` → 计数 **+1**
- 每次在本分支选择 `仍然执行 CR`，或触发下方兜底 → 重置为 **0**
- **计数 ≥ 5 时**：无论下一次变更是否 < 20 行，跳过本分支的询问，直接强制进入 Step 3 触发一次 CR，完成后重置为 0

> 目的：防止连续多次 < 20 行的改动通过本分支反复选择「跳过 CR」无限绕过 CR 门控。

#### Step 3：第 1 轮 CR

按上方「分片与 agentType 分级约束」决定 `SHARDS`。使用 `Agent` tool 启动 sub-agent，
**必须设置 `run_in_background: false`**（前台阻塞运行，防止主 session 提前结束）：
- `SHARDS = 1` → 单次 `Agent` 调用，`agentType: code-reviewer`，审查范围为本次全量增量 diff
- `SHARDS > 1` → **单条消息**内并行发出 `SHARDS` 次 `Agent` 调用，每次 `agentType: code-reviewer`，
  各自审查一份分片文件
  sub-agent 审查范围仅为本次增量 diff（或其分片），禁止触发全量分支扫描。

CR 完成后：

1. 在对话中输出**完整 CR 明细表格**（覆盖 sub-agent 报告的**每一条**问题，不得省略或只展示部分），表格**按严重程度排序**（Critical → High → Medium → Low，同级按文件路径+行号排序），每行含：编号、级别、文件:行号、问题描述、**推荐标记**（Critical/High 标注「🔴 建议修复」，Medium 标注「🟡 可选」，Low 标注「⚪ 不建议」）
2. 使用 `AskUserQuestion`（**multiSelect: true**）列出所有发现条目，让用户勾选要修复的条目：
   - 选项格式：`[级别] 文件:行号 — 问题描述`，选项顺序与上方明细表格一致（按严重程度排序）
   - 附加选项：`全选 Critical+High`（推荐）、`跳过所有修复`
3. 仅修复用户选中的条目；未选中的 Critical/High 条目追加进「已知问题持久化」文件（见上）；
   未选中的 Medium/Low 条目仅记录为 known issue，不做任何修改

#### Step 4：判定是否升第 2 轮

| 变更规模 | 第 1 轮用户选了 critical/high？ | 修复引入 > 50 行新代码？ | 第 2 轮 |
|---|---|---|---|
| 小 | — | — | ❌ 不触发 |
| 中 | 否 | — | ❌ 不触发 |
| 中 | 是 | 否 | ❌ 不触发（修复量小，回归风险低）|
| 中 | 是 | 是 | ✅ 触发 |
| 大 / 敏感 | — | — | ✅ 必触发（高风险兜底）|

#### Step 5：第 2 轮 CR（如触发）

审查范围收窄为**本轮修复实际改动的增量 diff**（即 Step 3.3 中被选中修复的条目所产生的代码变更），
不包含第 1 轮已审查通过、未被选中修复的原始代码。按该修复 diff 的行数/文件数重新套用「分片与
agentType 分级约束」评估 `SHARDS`（通常远小于 300 行，多数情况下 `SHARDS = 1`）。sub-agent 仍可按
「上下文补充许可」Read 被修复文件的完整当前内容以获取上下文，使用 `Agent` tool 启动，
**`run_in_background: false`**，分片并行方式同 Step 3。
CR 完成后同样按 Step 3 第 1 点要求展示**完整 CR 明细表格**（覆盖全部问题、按严重程度排序、含推荐修复标记），再通过 `AskUserQuestion`（multiSelect: true）让用户选择要修复的条目（顺序与表格一致）。
**第 2 轮结束直接完成 — 即使再发现 critical，也不升第 3 轮。** 用户未选择修复的残留问题在
commit message / PR description 中显式标记为 known issue / tech debt，同时按上方
「已知问题持久化」机制写入文件。

### 违规处理

未执行 sub-agent CR 即报告任务完成 = 流程违规，必须补执行。
