# 渐进式披露原则

## 核心理念

SKILL.md 是入口,不是百科。重内容下沉到 references,按需 Read 才进入上下文。

## 上下文预算意识

上下文窗口是公共资源。Agent 执行时要同时容纳系统提示、用户请求、对话历史、已触发 Skill、工具结果、代码片段和中间推理。Skill 多占一个 token,其他上下文就少一个 token。

写 Skill 时默认 Agent 已经很聪明,只补充它不知道、但完成任务必须知道的内容。每一段内容都应经受两个挑战:

1. **Agent 真的需要这段解释吗?** — 如果删掉它 Agent 不会搞错,就删掉
2. **这段内容值得它占用的 token 成本吗?** — 通用知识不值得,环境特定事实值得

## 何时拆 references(满足任一即应拆)

### 规则 1: SKILL.md 行数 > 80

主入口超过 80 行 → 必拆。目标:保持入口轻量。(本项目约定,官方规范为 < 500 行)

### 规则 2: 单个 Step 描述 > 30 行

某 Step 内联超过 30 行 → 拆为 `references/<step-name>.md`,SKILL.md 内只留一行引用。

### 规则 3: 多个 Step 引用同一规则

同一段约束被多处复用 → 拆为共享 reference。

### 规则 4: 内容可独立维护

某段内容有独立演进周期 → 拆为独立 reference 利于单独迭代。

## 何时不拆

- 单行/单段(<5 行) → 内联即可,拆分反而增加 Read 开销
- 仅在某 Step 末尾出现一次的小约束 → 内联
- 通用通识 → 写到 `## Constraints` 节内联

## 条件触发设计

Reference 实现"按需中的按需"——在 SKILL.md 中明确标注**何时触发读取**,而非无条件加载。

### 触发条件编写模式

```markdown
## 额外资源

仅在以下条件命中时读取对应 Reference:

- 当对话涉及**财务、预算、采购、费用报销**时:
  读取 [集团财务手册](references/finance-policy.md)

- 当对话涉及**API 认证失败、权限错误、Token 过期**时:
  读取 [认证排错指南](references/auth-troubleshooting.md)

- 当用户请求涉及**数据库 schema、迁移、表结构变更**时:
  读取 [数据库规范](references/db-schema.md)
```

### 触发条件设计原则

| 原则 | 说明 |
|------|------|
| 使用具体关键词 | "提到钱、预算、采购" 优于 "涉及财务" |
| 覆盖同义表达 | 列举多种措辞,防止模型漏判 |
| 避免过度宽泛 | 条件太模糊会导致无关场景也触发 |
| 默认不加载 | 设计为"条件触发"而非"条件排除" |

### 正反例

```markdown
<!-- 错误:条件太宽泛,几乎每次都会触发 -->
如果需要参考,读取 [guide.md](references/guide.md)

<!-- 正确:具体关键词触发,精准匹配 -->
当用户请求涉及**数据库 schema、迁移、表结构变更**时,
读取 [数据库规范](references/db-schema.md)
```

### 效果验证

设计完触发条件后,用两个场景检验:
- 场景 A 命中关键词 → 应触发读取 → 输出包含 reference 内容
- 场景 B 无关关键词 → 应跳过读取 → 节省 token

## 推荐 references 数量

| 复杂度 | 推荐数量 |
|---|---|
| 单步骤(<20 行总流程) | 0(无 references) |
| 多步骤(2-3 个 Step) | 2-4 个 |
| 多步骤(4+ 个 Step) | 4-6 个 |
| 分发判断 | 每分支 1 个 + 共享约束 1 个 |
