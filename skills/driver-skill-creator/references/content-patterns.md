# 高价值正文模式与脚本设计

## 知识萃取原则

**反模式:** 让 LLM 在没有领域上下文的情况下生成 skill,结果是泛泛而谈的指令("适当处理错误"、"遵循最佳实践")。

**正确做法:**
- 从真实任务中提取:成功步骤、纠正、输入输出格式、项目特定上下文
- 从现有工件合成:内部文档、API 规范、Code Review 评论、故障案例
- 每段内容必须通过"没有这条指令 Agent 会搞错吗?"测试,答案为否则删除

## 五种高价值正文模式

生成 skill body 时,必须选择至少一种模式应用。

### 1. Gotchas(陷阱提示) ★★★

**最高价值内容:** 列出违背合理假设的环境特定事实。

```markdown
## Gotchas
- `users` 表使用软删除。查询必须包含 `WHERE deleted_at IS NULL`。
- 用户 ID 在数据库中是 `user_id`,认证服务中是 `uid`,
  计费 API 中是 `accountId`。三者指向同一值。
- `/health` 只要 web 服务器运行就返回 200,即使数据库连接断了。
  使用 `/ready` 检查完整服务健康状态。
```

> 迭代提示:当 Agent 犯错你需要纠正时,将纠正添加到 Gotchas。

### 2. 输出格式模板 ★★★

提供模板比描述格式更可靠:

```markdown
## 报告结构
使用此模板:

# [分析标题]
## 执行摘要
[关键发现的一段话概述]
## 主要发现
- 发现 1 及支持数据
## 建议
1. 具体可执行的建议
```

### 3. 检查清单 ★★☆

```markdown
## 工作流
进度:
- [ ] 步骤 1: 分析表单 (运行 `scripts/analyze.py`)
- [ ] 步骤 2: 创建映射 (编辑 `fields.json`)
- [ ] 步骤 3: 验证 (运行 `scripts/validate.py`)
```

### 4. 验证循环 ★★★

```markdown
## 编辑流程
1. 执行编辑
2. 运行验证: `python scripts/validate.py output/`
3. 如果验证失败: 查看错误 → 修复 → 再次验证
4. 仅在验证通过后继续
```

### 5. 计划-验证-执行 ★★★

用于批量或破坏性操作:

```markdown
## 数据迁移
1. 提取 schema: `scripts/analyze.py input.db`
2. 创建映射文件 `mapping.json`
3. 验证: `scripts/validate.py mapping.json`
4. 验证失败 → 修改并重新验证
5. 执行: `scripts/migrate.py --mapping mapping.json`
```

## 指令具体度匹配

| 场景 | 策略 |
|------|------|
| 多种方法有效、任务容错、结果可变 | 宽松指令,给 Agent 自由 |
| 操作脆弱、一致性关键、序列敏感 | 严格指令,精确步骤,不允许偏离 |

## 行为链路 7 点

一个有效的 Skill 应覆盖 Agent 的完整行为链路。Step 1 推断时逐项确认:

| # | 检查点 | 在 Skill 中的体现 |
|---|--------|-----------------|
| 1 | 什么时候发现这个 Skill | `description` 的触发关键词覆盖度 |
| 2 | 什么时候加载完整正文 | 发现层与执行层分离(见 frontmatter-spec.md) |
| 3 | 哪些信息继续按需读取 | references 的条件触发设计 |
| 4 | 哪些动作必须先做 | `<HARD-GATE>` 门控 |
| 5 | 哪些行为绝对不能发生 | Constraints / Gotchas 中的禁止项 |
| 6 | 如何证明任务真的完成 | 验证循环 / 检查清单 |
| 7 | 什么时候需要停下来请求人类判断 | AskUserQuestion 门控点 |

> 如果某个 Skill 在第 4-7 项上全部空白,它更像提示词模板而非能力包。

## 门控（Gate）机制

在低自由度任务里,门控尤其重要。Skill 如果只写"**建议**先做 A",Agent 很可能直接进入 B。门控的作用是:**在条件满足前,明确禁止后续动作。**

**四种门控类型及示例:**

| 门控类型 | 说明 |
|---------|------|
| 前置条件门控 | 条件满足前禁止后续动作 |
| 质量门控 | 验证通过前禁止提交 |
| 人类审批门控 | 高风险操作必须等待人类确认 |
| 资源检查门控 | 依赖就绪前禁止执行 |

① 前置条件门控:

```xml
<HARD-GATE>
在用户提供目标数据库的连接字符串之前,
禁止生成迁移脚本或执行任何 SQL 操作。
缺少连接信息 → AskUserQuestion 追问,
不得使用占位符或假设默认数据库。
</HARD-GATE>
```

② 质量门控:

```xml
<HARD-GATE>
代码变更必须满足以下全部条件才能提交:
1. `flutter analyze` 零警告
2. 所有现有测试通过
3. 新增代码的测试覆盖率 ≥ 80%
任一条件未满足 → 修复后重新验证,
禁止跳过或降低标准。
</HARD-GATE>
```

③ 人类审批门控:

```xml
<HARD-GATE>
以下操作必须通过 AskUserQuestion 获得
用户明确确认后才能执行:
- 删除任何生产环境数据
- 修改权限或认证配置
- 执行不可逆的 schema 迁移
用户未确认 → 展示操作影响摘要并等待,
禁止以"用户之前同意过"为由跳过确认。
</HARD-GATE>
```

④ 资源检查门控:

```xml
<HARD-GATE>
执行部署前必须验证:
1. `.env.production` 存在且包含必需的 API_KEY、DB_URL、SECRET
2. Docker daemon 正在运行
3. 目标 registry 可达（curl 健康检查通过）
任一资源不可用 → 报告缺失项并停止,
禁止使用开发环境配置替代。
</HARD-GATE>
```

**何时使用门控?**

判断标准:**如果 Agent 跳过这一步,后果是否不可逆或代价高昂?**

| 场景 | 是否需要 | 原因 |
|---|---|---|
| 操作生产数据库 | ✅ 必须 | 误操作不可逆 |
| 生成代码前需确认架构 | ✅ 必须 | 返工成本高 |
| 格式化输出为 markdown | ❌ 不需要 | 错了重跑即可 |
| 发送通知/邮件 | ✅ 必须 | 发出后无法撤回 |
| 本地文件读取分析 | ❌ 不需要 | 只读操作无副作用 |

**放置位置规则:**

`<HARD-GATE>` 必须放在 Agent 即将做出被守护动作的那一步被读到的位置:

| 放置位置 | 用法 |
|---|---|
| `### Step N` 内部 | 守护该步骤的前置条件(最常见) |
| `## Constraints` 内部 | 跨步骤生效的全局性禁令 |
| 条件分支入口处 | 某分支需要额外约束时 |

禁止放置的位置:
- ❌ frontmatter 内(不会被解析为指令)
- ❌ references/ 子文件中(Agent 可能还没读到就已经行动)
- ❌ `## Workflow` 标题同级(层级太高,缺乏步骤上下文)

**必须用 `<HARD-GATE>` 标签吗?**

不是必须的。门控的本质是语义上的强制禁令,不依赖特定标签语法。`**禁止**...` 或 `> ⚠️ 必须...违反则回退` 同样有效。`<HARD-GATE>` 的优势是视觉醒目 + 结构化——长篇 SKILL.md 中更易识别。短小的单步骤 Skill 用加粗措辞即可。

> 门控不是语气问题,而是执行边界。减少 Agent 的解释空间,让关键路径更像程序。

## 自由度三档分级

| 自由度 | 控制方式 | 适用场景 |
|--------|---------|---------|
| 高自由度 | 结构原则、语气规则、示例引导 | 写技术文章、代码审查 |
| 中自由度 | SQL 模板、字段说明、口径控制 | 查询内部指标、数据分析 |
| 低自由度 | 脚本保证确定性 + 门控 | 旋转 PDF、部署、生成固定报告 |

常见错误:
- 把脆弱操作写成开放建议(应该用脚本 + 门控)
- 把需要判断的任务写成死流程(应该给自由度)

## 对抗合理化（Anti-Rationalization）

Agent 在压力下会给跳过规则找到听起来合理的理由。Skill 需要提前写出借口并反驳:

| Agent 的合理化借口 | Skill 应写入的反驳 |
|-------------------|-------------------|
| "这只是一个简单修改" | 简单修改也需要走完整验证流程 |
| "我已经知道答案了" | 知道答案 ≠ 验证过答案 |
| "上下文快满了,跳过验证" | 上下文不足时应请求人类判断,而非跳过步骤 |
| "这个规则不适用于当前场景" | 规则的适用性由 Skill 定义,不由 Agent 自行解释 |

**生成 Skill 时,Step 2 提案中必须至少包含 2 条针对目标任务的对抗合理化条目。**

## 信息单一来源

不要在 SKILL.md 和 references/ 中重复同一段规则。重复会带来漂移,漂移会让 Agent 在两个版本之间自行解释。

- 程序性知识(如何做) → SKILL.md 正文
- 参考知识(查阅用) → references/
- 同一规则只放一个地方,其余引用

## 内容编写原则

- **提供默认值,而非菜单** — "使用 pdfplumber" 优于 "可选 pypdf/pdfplumber/PyMuPDF"
- **偏重流程而非声明** — 教 Agent 如何处理一类问题,非对特定实例产出什么
- **解释 why** — "做 X 因为 Y 容易导致 Z" 比 "总是做 X" 更有效
- **适度详细** — 简洁的分步指导 + 工作示例优于详尽文档;过于全面的 skill 反而有害

## Skill 间引用

Skill 之间可以互相引用,但应声明关系层级:

| 引用层级 | 语法 | 说明 |
|---------|------|------|
| Required | `**必需子 Skill：** 先使用 skill-x` | 前置依赖,必须先执行 |
| Recommended | `**推荐：** 使用 skill-y` | 可选增强,视场景使用 |
| See Also | `**另见：** openai_yaml.md` | 参考信息,不影响执行 |

不要用一次性强制加载大量内容的方式组合 Skill,那会破坏渐进披露。

## 平台适配

不同平台的工具名可能不同。Skill 应写行为规则,再用平台层适配:

- 平台能力不足时优雅降级
- 真正应该稳定的是行为规则,不是某个平台的私有工具名

## 脚本设计原则

含 `scripts/` 目录的 skill 必须遵守:

### 核心概念:Script 只执行不读取

Agent 执行 Script 时不会把代码加载到上下文,只看执行结果。因此:
- 哪怕脚本有 1 万行,token 消耗也几乎为零
- 复杂逻辑放心封装在脚本中(文件上传、API 调用、数据转换、构建部署)

### 硬性要求

- **禁止交互式提示** — Agent 在非交互式 shell 运行,无法响应 TTY
- 缺少必填参数 → 输出清晰错误和用法示例,非挂起等待输入

```bash
# 错误: 挂起等待输入
$ python scripts/deploy.py
目标环境: _

# 正确: 清晰的错误和指导
$ python scripts/deploy.py
错误: --env 为必填参数。可选值: development, staging, production。
用法: python scripts/deploy.py --env staging --tag v1.2.3
```

### 推荐实践

| 原则 | 说明 |
|------|------|
| `--help` | 复杂脚本必须提供用法文档和示例 |
| 结构化输出 | JSON/CSV/TSV 到 stdout,诊断信息到 stderr |
| 幂等性 | "如不存在则创建" 比 "创建并重复时失败" 更安全 |
| Dry-run | 破坏性操作提供 `--dry-run` 标志 |
| 退出码 | 不同失败类型使用不同退出码并在 `--help` 中文档化 |
| 安全默认值 | 破坏性操作需 `--confirm` / `--force` 标志 |
| 输出可预测 | 默认输出摘要;大量数据支持 `--output` 标志 |

## Script vs Reference 决策指南

核心判断:**Agent 需要「理解内容再行动」还是「执行命令看结果」?**

| 判断维度 | 放 `scripts/` | 放 `references/` |
|---|---|---|
| Agent 是否需要阅读内容 | ❌ 不读取,只执行 | ✅ 读取后据此推理 |
| Token 消耗 | ≈ 0(仅消耗 stdout) | = 文件大小 |
| 输出确定性 | 高(同输入 = 同输出) | 低(模型每次推理可能不同) |
| 典型内容 | 数据处理、API 调用、格式转换、构建部署 | 领域知识、排错指南、规范文档、Schema 定义 |
| 可维护性焦点 | 代码正确性(单测、CI) | 内容时效性(定期审查) |

**快速判定规则:**

```
IF 操作有确定性输入输出(同输入必须同结果)
  → scripts/(消除模型推理波动)

ELSE IF 内容是 Agent 推理时需要参考的知识
  → references/(按需加载到上下文)

ELSE IF 内容是被复制/修改的模板或素材
  → assets/(不读入上下文,作为输出材料)
```

**灰色地带:** Agent 是否需要根据内容做推理判断?
- 需要推理(如根据上下文选择映射策略) → `references/`
- 不需要推理(如固定的 A→B 转换) → 写成脚本,零歧义

> 经验法则:如果 Agent 对同一任务每次产出不同结果且差异不可接受——把那段逻辑从 reference 提升为 script。
