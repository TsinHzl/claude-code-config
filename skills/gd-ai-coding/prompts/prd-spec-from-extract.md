# 从标准 PRD 抽出结果写 prd-spec.md

主编排在 `dac-prd-mode=standard` 时使用本 prompt（输入是 `prd-extract.json`，不是精裁后的散文）。规则与列/行/理解文档一致，不要发明页面名特例。

## 输入文件

- `openspec/changes/{req_name}/prd/prd-extract.json`
- `openspec/changes/{req_name}/prd/prd-clarify.md`（可空）
- `openspec/changes/{req_name}/ui/index.json`（如已按有效 UI 链拉过 DSL）
- 模板：`${DAC_SKILL_HOME:?DAC_SKILL_HOME 未解析}/templates/tpl-prd-spec.md`

只对**这一个**功能点阅读：合并后的 `detail_segments` + 该点线上图/需求图/详情附图 + `valid==true` 的 UI 链。不看其它功能点的详情，不看合作方整表。例外：`trackings_unmatched` 要对照各功能详情，见下方结构条。

## 禁止

- 没写的状态 / 接口 / 数值 / 文案不要编
- 不要把详情原文整段粘进「需求描述」当完成
- 不要把「无开发」当成类型「复用」，也不要把「复用」当成无开发
- 模板有「UI 状态」三项：详情没写到的填「无」，不要补骨架屏/空态/错误态
- 空 API 且详情已写后端下发 / 已有接口 → 不问、不编契约
- 无 `layer_id` 的链不当设计稿

## 类型（§2 / §3.x）

只认详情用语：新增页面 / 端上新增 / 新建 / 新功能 → 新增；复用 / 沿用 / 保持不变 → 复用；修改 / 调整 / 优化 → 修改；都没有 → **修改**。

`no_dev==true` 或详情出现「无开发」：类型仍按上表；§2 说明写明无开发。该点必须出现在 §2 和 §3.x。

## 结构

- §1：`background` + `scope` 压成 2～3 句，不要抄各功能详情
- §2：每个 `features[]` 一行，顺序与 JSON 一致；缺名用「（缺功能名）」
- §3.x：一个功能点一节；多段 `detail_segments` 写成一节里的分段，不要揉掉
- 设计稿：有 index.json 时填 `ds_xxx（节点名）`，否则可先写有效 URL；无有效链 → 无
- 挂上的埋点进该节。`trackings_unmatched`：读整行（页名、点位名、时机、event_id、图）对照功能详情；**只有一处对得上**就写入该节，不要只因页名≠功能名整表打回。两处都像或哪都不像 → 问一句挂哪；不要把未挂上拆成一串澄清。理解后仍挂不上的：放在最后一个 `### 3.x` 之后、§4 之前，标题写成 **`### 未挂上的埋点`**，禁止 `### 3.6` 这类编号（否则 coverage 会当成新需求点）
- §4 兼容性：scope 各维度原文（值空写成「某维：无」）；性能没写 → 无
- §5：只放问过仍未决、或会挡实现的缺口。空语言、空 API、没写的 UI 状态 **不要**自动进 §5。页名对不上但已唯一挂上的埋点 **不要**进 §5

## 澄清（写 spec 时）

只问读懂之后仍会做错实现的点（图文打架、互斥样式无触发条件、必做交互完全没写、类型用语冲突、非无开发但设计对不齐、某条未挂上埋点读完整行后仍对得上两处或哪都不像）。页名≠功能名但整行已唯一对上 → 直接挂，不算澄清。

- 0～2 条：正常，问完写入对应 §3.x
- 3～5 条：问，开头说明文档这几处没写死
- **>5 条或同一页反复缺触发/结果：** 停下来告诉用户「这份标准表还不能当实现输入」，列出缺的槽，不要开 Cooper 式长澄清
