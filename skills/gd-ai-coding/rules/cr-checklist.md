# AI CR 检查清单（需求变更维度）

本检查清单专用于 `dac-code-review` skill，只检查与当前功能需求直接相关的代码改动。

## 输出规则

**只输出不通过的项。** 逐维度检查，通过的项不输出、不列举、不解释。全部通过时直接返回 `verdict: clean`。

## 优先级说明

- 🔴 **严重**：必须修复，会导致功能缺失、数据错误、或无法上线
- 🟡 **一般**：建议修复，影响功能质量或可维护性
- 🔵 **建议**：可选优化，不阻塞本次功能交付

---

## 1. 功能完整性 🔴

- [ ] 需求文档中每个功能点都有对应的代码实现
- [ ] 功能的验收标准每一条都可追溯到具体实现
- [ ] 设计稿中的所有页面状态都有处理：
  - [ ] 正常状态（有数据）
  - [ ] 加载中状态
  - [ ] 空态（无数据）
  - [ ] 错误状态（网络错误、业务错误）
- [ ] 权限或登录状态边界有处理（需求有要求时）

---

## 2. 接口与数据正确性 🔴

- [ ] 调用的接口路径（URL）与接口文档一致
- [ ] HTTP 方法（GET/POST/PUT/DELETE）与接口文档一致
- [ ] 请求参数字段名与接口文档一致（注意 camelCase / snake_case 转换）
- [ ] 请求参数类型与接口文档一致（String vs int vs bool）
- [ ] 必填参数有传递，非必填参数按需传递
- [ ] 响应数据解析字段与接口文档一致
- [ ] 接口错误码有对应的错误处理逻辑
- [ ] JSON 序列化/反序列化与 JSON 数据格式定义一致

---

## 3. UI 规格符合性 🟡

- [ ] 页面组件层级结构与设计稿描述一致
- [ ] 文案内容（标题、按钮、提示文字）与设计稿/需求一致
- [ ] 空态展示内容与规格文档描述一致
- [ ] 错误提示文案与需求/设计规格一致
- [ ] 列表项展示的字段与设计稿一致

---

## 3.5 设计稿-代码结构一致性 🟡（type=page/component 且 ui_dsl.json 存在时）

> 仅在功能 type 为 page/component、ui_dsl.json 存在、且 `.design_skipped` 标记文件不存在时检查。

- [ ] `ui_tree.txt` 层级结构与代码 Widget 嵌套结构一致
- [ ] `ui_dsl.json` 中 componentInfo 标记的组件实例在代码中有对应 Widget 使用
- [ ] `ui_dsl.json` 中颜色/字体通过 theme 或常量引用（非硬编码值）
- [ ] `ui_dsl.json` 中 TEXT 节点的 content 与代码实际文案一致

---

## 4. 交互逻辑正确性 🔴

- [ ] 用户操作后的路由跳转目标与需求一致
- [ ] 表单提交的触发条件与需求一致（如：按钮何时可点击）
- [ ] 操作成功/失败后的用户反馈与需求一致（Toast、弹窗、跳转）
- [ ] 涉及的弹窗内容和操作与需求一致
- [ ] 页面间数据传递正确（传入参数、返回结果）

---

## 5. 边界与异常处理 🟡

- [ ] 网络请求有超时处理
- [ ] 网络请求有重试策略（如需求要求）
- [ ] 用户输入有基础校验（如需求中有校验规则）
- [ ] 空指针/空数据不会导致 UI 崩溃

---

## 6. 平台一致性 🟡（Flutter 特有）

- [ ] 功能在 iOS 和 Android 上的关键行为一致
- [ ] 涉及键盘弹出时，输入框不被遮挡（两端验证）
- [ ] 底部安全区域（Home 指示器）有处理
- [ ] 有平台差异的代码有注释说明原因

---

## CR 不检查的范围（超出本次需求）

以下问题不在本次需求变更 CR 范围内，不阻塞功能交付：
- 与本次需求无关的代码质量问题
- 全局架构优化建议
- 与本次需求无关的性能优化
- 测试覆盖率（已前置解耦至 Phase 3 步骤 4.5「测试用例生成与验证」：逻辑/数据类需求点由生成的可执行
  测试通过 `flutter test` 实际验证，UI/交互类需求点由独立 sub-agent 推理判断场景清单 pass/fail；
  该环节独立于本 CR，非本 CR 职责范围，不代表本清单遗漏）
- 文档完整性（API Doc、README）

如发现上述问题，可以在 CR 报告的「建议」节中提及，但标记为 🔵 级别。
